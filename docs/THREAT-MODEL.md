# Security threat model

## Assets

1. The user's games, saves and store installations. These must never be modified or broken.
2. Store accounts and credentials. VYSTRAL never touches them.
3. The local library database, notes, sessions and media folders.
4. The PC's integrity: no elevation, no arbitrary code execution, no hardware changes.

## Trust boundaries

| Boundary | Untrusted input | Controls |
|---|---|---|
| Web UI → native bridge | Every message (the UI could be compromised by malicious metadata) | Allow-listed methods; typed params with unknown members rejected; ID regex; length and control-character limits; no paths from the UI (native pickers only); 256 KB message cap; source-origin check (`https://app.vystral.example` only) |
| Store manifests & registry | Malformed or hostile VDF/JSON/XML, odd paths | Tolerant parsers that throw only `FormatException`; VDF depth limit; XML with DTD processing disabled; `..` path escapes rejected; read-only registry interface |
| Launch targets | URIs and exe paths from manifests and user launch options | Per-platform URI scheme allow-list; no whitespace or control characters in URIs; AUMID regex; `.exe` only; must be inside the game's install folder (store games); no UNC paths; CreateProcess with an argument list (no shell parsing) |
| Network metadata/artwork | Steam store JSON, images | HTTPS only; 12 MB cap; content-type and magic-byte checks (JPEG/PNG/WebP); atomic writes into a private cache; HTML stripped and entities decoded; rendered as React text (never `innerHTML`) |
| Media folders | User-chosen folders, crafted URLs | Served only via a filtered handler: path normalized and required to stay under an approved root, image/video extensions only, feature off by default |
| Local AI (Ollama) | Model output | The model cannot call anything. Structured output is validated against a whitelist schema. Suggested actions still require a user click through the normal bridge. |
| Cloud AI keys (Track C5) | User-provided Anthropic / OpenAI / Google / OpenAI-compatible keys; the compatible endpoint's address | Stored only in Credential Manager (`VYSTRAL/AI-<Provider>`), never in SQLite, settings, logs or bridge responses (the page gets “…1234”); format-checked (16–250 of `A-Z a-z 0-9 - _ .`, a key for another provider is caught before any request) and saved only after the provider's free models list accepts it. Sent only as a header (`x-api-key`, `Authorization: Bearer`, `x-goog-api-key`) to that provider's fixed host, or to the user's endpoint, which must be `https://` with no user info, query or fragment. The cloud AI client never follows redirects (custom key headers would follow them). Provider error text is never shown (some echo part of the key); fixed messages are used instead. |
| Cloud AI requests and answers (Track C5) | Model output; provider JSON | Off by default and per-provider opt-in; nothing in Offline mode or safe mode. One serialized lane per provider (≥ 1 s apart, `Retry-After` pause on 429), a local budget (30 per 10 min, 400 a day), 60 s per request, 2 MB answer cap, only provider and URL path logged. Each feature sends a fixed, documented set of facts (no paths, notes or IDs). Model output is untrusted: JSON is parsed with depth/size limits and validated against closed schemas (journal query spec, smart-collection filter, tonight plan by candidate reference only); unknown enum values, wrong types and out-of-range numbers reject the answer. Every sentence shown may only contain numbers VYSTRAL supplied (anything else is discarded for VYSTRAL's own deterministic wording); text is cleaned of control and bidi characters and rendered as React text. Picks can only reference VYSTRAL's own candidates, and “Open” only navigates. Prompt instructions tell the model to ignore instructions inside news posts; even if it doesn't, its output can only become validated text. |
| Smart collection rules (Track C5) | `rule_json` on a collection (from the page or a model) | Validated natively on save (closed schema, ≤ 4,000 chars, canonical re-serialization) and re-validated by the page on every read; a rule only filters the library, it never changes it. |
| Steam Web API key | User-provided key | Stored only in Windows Credential Manager (generic credential `VYSTRAL/SteamWebApiKey`), never in SQLite, logs or bridge responses; requests go only to `api.steampowered.com`; stored only after Steam accepts it |
| Data-source keys (SteamGridDB, IGDB/Twitch, RAWG, IsThereAnyDeal) | User-provided keys and Twitch client secret | The user's own keys only (none ship in the binary, since anything embedded in an open-source app is public). Stored only in Credential Manager (`VYSTRAL/<Source>`), never in SQLite, logs or bridge responses (the page gets a masked suffix); saved only after the provider accepts a test request. The Twitch secret goes in a form body, never a URL; the IGDB token stays in memory. Keys are sent only to their own provider's host, as a header where the API allows (SteamGridDB Bearer, ITAD `ITAD-API-Key`, IGDB `Client-ID`/Bearer); RAWG requires a query parameter, so request logs record only the provider and URL path |
| Data-source answers (SteamGridDB, IGDB, RAWG, CheapShark, IsThereAnyDeal, Wikidata, Steam store, AreWeAntiCheatYet) | JSON from eight outbound hosts | HTTPS only; one serialized, spaced lane per provider with a `Retry-After`-aware pause on 429; 4 MB answer cap (8 MB for the anti-cheat list); a 30 s limit on the whole request, body included, so a server that stalls mid-answer can't hold a provider's lane (streamed images and video files have a 60 s limit); tolerant parsing where wrong types count as missing; text stripped of markup, clipped and rendered as React text; IDs, slugs, currencies and URLs validated by pattern (image URLs must be HTTPS on `steamgriddb.com`); numbers clamped; Wikidata values checked per property before any link is built; exact-title matches only when unique (and year-consistent), never overwriting existing or user-set fields |
| Friends' public status and avatars (Track P, opt-in) | Persona names, game names, game IDs and avatar URLs from `GetPlayerSummaries`; the friends list from `GetFriendList` | Requests only to `api.steampowered.com` through the shared, serialized Steam Web API client (key never logged); SteamIDs validated (17 digits, `7656119…`), at most 3,000 friends, states clamped to 0–6, names stripped of control and bidi/format characters and clipped (64 / 128 chars), only 32-bit app IDs used to match the library. The page never sees SteamIDs (opaque hashed keys). Avatar URLs must be HTTPS on Steam's avatar hosts with a hash-shaped path (no query, port or user info; redirects to other hosts rejected); each image ≤ 256 KB, image content type and JPEG/PNG/WebP magic bytes, written atomically into `cache\_avatars` (≤ 400 files) and served through the art host. Nothing is persisted except those images |
| Steam app manifests for the update forecast (Track P) | Byte counters and flags in `appmanifest_*.acf` | Read-only; files over 256 KB skipped; tolerant VDF parsing; negative or non-numeric counters become 0; names cleaned and clipped; build IDs digits only. Actions offered are navigation only (Storage Studio, the game's existing *Open install folder*); nothing is deleted or started |
| Art picker images | Community images from SteamGridDB | Same rules as other artwork: HTTPS, size caps (3 MB preview, 12 MB full), image content type, magic-byte sniffing, atomic writes into the private cache, served through the art host (the page never loads remote images). The page refers to images only by an opaque option ID from the last native listing |
| Outbound links (deals, “Open on…”, attribution) | URLs from providers or built from IDs | The page never sends a URL: deal links are looked up natively from the cached answer by opaque offer ID and must be plain HTTPS; store/site links are built natively from validated IDs; fixed attribution links come from a native table. Links open in the default browser, never inside VYSTRAL |
| Trailers | Steam HLS playlists and segments | Filtered proxy: HTTPS Steam video CDN only, the exact appid's folder, fixed file-name patterns, size caps, VYSTRAL-set content types, no redirects, nothing written to disk |
| Live tiles (`https://media.vystral.example/live/{gameId}/{key}.mp4`) | Steam micro-trailer files; crafted proxy paths from a compromised page | The page can only name a game id and a 16-hex key (`^/live/[0-9a-f]{32}/[0-9a-f]{16}\.mp4$`); the upstream URL is never taken from the page but derived natively from the stored, already-validated HLS trailer (same allow-listed HTTPS host, same appid folder, fixed file name `microtrailer.mp4`) and must hash to the requested key. Dedicated client with no redirects and no decompression; 6 MB cap (Content-Length and streamed); body must start with an MP4 `ftyp` box; written atomically into `cache\live` under a VYSTRAL-chosen name (`{gameId}-{key}.mp4`), LRU-capped at 160 MB; served with a fixed `video/mp4` type and `nosniff`. No download in Offline mode, Data saver or while a game runs; nothing served at all while a game runs or with the setting off. The page never hot-links Steam (CSP `media-src` allows only the media host and `blob:`). |
| Session replay images (Track M) | PNG bytes rendered by the page, sent in base64 chunks | The page never names a path or file: `replay.imageBegin` binds an upload to an existing finished session, uploads expire after 2 minutes (at most 2 at once), chunks must arrive in order and stay under the 256 K-character message cap, the total is capped at 20 MB and must match the announced size, and the bytes must be a PNG whose IHDR is exactly 1920×1080 and that ends in IEND. Saving always goes through the native save dialog with a file name built natively from the game title and date; copying goes only to the Windows clipboard. Sale-calendar “Source” opens a URL from the shipped, validated file (https on a Valve domain), never one from the page |
| Other processes (background-app report) | Process names and counters of everything running | Read with one handle-free `NtQuerySystemInformation(SystemProcessInformation)` call every ~30 s of a session: no process is opened, so protected and anti-cheat processes are never touched. Only executable file names (no paths, titles or command lines) and memory/CPU figures are kept; names hidden by the user are filtered on read; `insights.hideBackgroundApp` accepts only a file-name-shaped string (≤ 128 chars, no path characters) |
| Game detection (games started outside VYSTRAL, opt-in) | Every process on the system, while the app or background tracker watches | No process is ever opened: the list comes from `NtQuerySystemInformation(SystemProcessInformation)` and executable paths from `SystemProcessIdInformation` (both handle-free, so anti-cheat and protected processes are never touched); the foreground window's owner from `GetForegroundWindow`/`GetWindowThreadProcessId`. Only processes in the user's own Windows session are considered. Paths are matched in memory against install folders and never stored; only the matched game's id and times are recorded |
| Background tracker process (opt-in) | Its own command line; the coordination objects; the state files | The same binary as the app (`Vystral.exe --background-tracker`), started per-user at sign-in, never elevated. The command line must be exactly the switch (plus a development-only `--data-dir <absolute local folder>`); anything else starts the normal app. It has no window, bridge, WebView2, network access or listening endpoint |
| Inter-process coordination | Named mutexes/events in the session-local namespace (`Local\VYSTRAL-<hash>-…`) | They carry no data, only "open / tracking / yield / stop / migrating". Any program running as the same user could signal or hold them; the worst effect is that games aren't noticed (or the tracker exits), which that program could cause anyway. Hand-over data travels only through `tracker-session.json` in the user's data folder; it is size-capped, fully validated (32-hex ids, known source values, sane times) and can only continue or close a session that already exists and is open |
| Sign-in entry | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, value `VYSTRAL Background Tracker` | Written only by the installed app when the user turns the setting on, with a fixed command: the quoted Velopack launcher path (validated: local, absolute, `.exe`, no quotes or `%`) and `--background-tracker`. Development and portable copies never write or remove it. Removed when the setting is turned off and on uninstall; only this one value name is ever touched. Task Manager's own on/off switch is respected and shown |
| GPU driver identity | NVML strings, display-adapter registry values | Read-only NVML (`nvmlSystemGetDriverVersion`, `nvmlDeviceGetName`) or the read-only registry interface; values are trimmed, stripped of control characters and length-capped (64/128) before storage; shown as React text |
| Updates | Release packages | Velopack downloads over HTTPS from the project's GitHub releases and verifies SHA hashes from the release feed before applying. The installer is unsigned for now (see limitations). Updates never apply while a game is starting or running. Offline mode blocks every check and download, including the ones started from Settings; Data saver (or a metered connection) stops the background download. One download at a time. "Restart to update" runs VYSTRAL's clean-exit path (session hand-over, clean-exit record, log flush) before Velopack restarts the process. |
| Rollback package | The previous version's `.nupkg` kept in the data folder (`update/rollback`), which other same-user programs can write to | Preserved from Velopack's own verified packages folder just before an update downloads; its SHA-256 (and SHA-1) is recorded at that moment in `package.json`. Before applying, the size and SHA-256 are checked again and the rollback is abandoned on any mismatch; Velopack then verifies the file against the feed hashes again while copying it into its packages folder. The manifest's file name must be a plain `*.nupkg` name (no path separators or `..`). A rollback only ever targets the last version that started successfully, only downgrades, happens at most once per version, never in safe mode or development builds, and is logged. |
| Network health | User-initiated checks | Only on "Check now"; fixed, hard-coded keyless endpoints (`/rate_limit` on GitHub's API, Steam's `GetServerInfo`, a header image, the trailer CDN root); headers only, bodies are never read; no Steam key or cookies are sent; Offline mode skips every non-local probe |
| URI scheme / notification activation | `vystral:` URIs (any app or web page can launch a registered scheme; browsers ask first) and the command line they produce | Navigation only: a URI can open one of nine pages and nothing else; it never launches a game, runs a fix, changes a setting or reads a path. Parsed by hand (no unescaping or normalisation): fixed `vystral://open?…` shape, 512-character cap, printable ASCII only, no percent-escapes, no duplicate or unknown parameters, route name allow-list, `id`/`sessionId` must be 32 lowercase hex, `section` 1–24 lowercase letters, each parameter only on its own route. The registered command is `"<exe>" --uri "%1"`; the process accepts it only when the command line is exactly those two arguments, so quote-injected extras (including `--safe-mode` or Velopack hook switches, which must be the first argument) are ignored. Rejected URIs are logged by length only and treated as a plain launch (bring the window forward). Registry writes are per-user (`HKCU\Software\Classes`) and repaired on start; uninstall removes them only if they still point at that copy. |
| Cloud catalogues and launch (opt-in) | Public GeForce NOW and Game Pass catalogue JSON, Microsoft Store product details, the GeForce NOW Statuspage feed | Off by default; at most one refresh a day per market, back-off on 429/5xx, no cookies, no redirects, size-capped answers; every ID is validated (UUID, digits-only cmsId, 12-character product ID, package family name) before use. Launches build each argument as a separate list item from validated IDs only; only fixed `https` vendor pages and `msxbox:` go through the shell; the stream always runs in the vendor's app or a separate Edge profile VYSTRAL never reads. |
| Steam Input layouts | VDF files in Steam's folder (user-writable) | Read-only; paths must resolve inside Steam's folder (links out are refused); ≤ 2 MB, nesting ≤ 24, capped groups/presets/bindings; `localconfig.vdf` is never read. |
| Universal search and Discover pages | Steam store search/appdetails, Wikidata SPARQL, IGDB and RAWG answers, image downloads | Each source behind its own switch; Offline mode sends nothing; size-capped validated parsers; strict item keys (`steam-<id>`, `igdb-<id>`, `rawg-<slug>`, `wd-<QID>`); images only from allow-listed CDNs through the artwork pipeline; store links built natively from validated IDs and opened in the browser only. |
| Subscription catalogues and queue alerts | Public Game Pass lists, Store product details, GeForce NOW window titles | Opt-in, daily, size-capped, re-validated JSON cache; product IDs validated; queue titles read with `EnumWindows`/`GetWindowText` only while a VYSTRAL-started session waits, parsed strictly; no clicks, memory reads or injection. |
| Steam wishlist, news, friends' recent games | Steam Web API and community news (BBCode/HTML) | The user's key from Credential Manager; news parsed into fixed plain blocks (no HTML is rendered, links keep their text, control and bidi characters stripped); images only from Steam CDN hosts via the artwork checks; avatars and keys kept opaque. |
| Files tab, uninstall advisor and save locator | PCGamingWiki wikitext paths, Workshop manifests, mod-manager folders, Steam Cloud markers | Read-only; PCGamingWiki path tokens expanded strictly (registry, UNC, drive-letter, `..` and reserved characters refused; every result re-checked to stay under its root); folder opening only by IDs from the last listing; the only new shell link is the fixed `ms-settings:appsfeatures`. |
| Cached first paint | `ui-state/first-paint.json` (other same-user programs can write it) | Structure and size checked, version-stamped, re-serialized before it's injected as a JSON literal; the UI re-validates every field and accepts art only from the art cache; a bad file falls back to the live path. |
| Startup history and title bar regions (Track C2) | VYSTRAL's own log files (other same-user programs can write them); drag/passthrough rectangles from the page | `diagnostics.startupHistory` takes only a limit (1–50) and never a path: it reads only `logs\vystral-YYYYMMDD.log` in the data folder (reparse points skipped), newest 10 files, at most the last 16 MB and 200,000 lines of each, parses only lines that mention the startup message (≤ 64 KB, JSON depth ≤ 8, ≤ 64 numbers, each 0–600,000 ms) and returns numbers and a timestamp. `window.dragRegions` accepts at most 16 caption and 32 passthrough rectangles, each finite and within a sane window area. |
| WebView2 | Navigation, popups, downloads, permissions | Navigation outside the app origin is cancelled; new windows, downloads and permission requests are denied; host objects, dev tools, context menus, autofill and password saving are disabled in release; CSP `default-src 'self'` |

## Explicit non-goals (never implemented)

DLL injection, overlays inside game processes, memory reading, DRM or anti-cheat interaction, reading tokens/cookies/passwords, private or reverse-engineered APIs, overclocking/undervolting, fan or power-limit changes, killing Windows services, disabling security features, and running elevated (the app manifest is `asInvoker`).

**The one elevated action:** if the user turns on frame-rate capture, VYSTRAL can, on an explicit button press, add the signed-in account to Windows' *Performance Log Users* group (`net localgroup … /add`, one UAC prompt). That group is what Windows requires for ETW frame tracing. VYSTRAL itself never runs elevated, and PresentMon is downloaded only on request and SHA-256-verified against a pinned hash before every run, including the short run that ends its capture session (if the file changed meanwhile, the capture process is ended directly and the file isn't run again).

## Residual risks

- **Unsigned binaries.** SmartScreen warns, and users must trust the GitHub release page. Mitigation: download only from Releases. Adding code signing is on the roadmap.
- **Update channel trust.** Updates trust the GitHub repository. If the repository or the owner's token were compromised, a malicious update could be published. Mitigations: repository two-factor authentication; releases are built only by CI from tags.
- **Process detection** for games launched *from* VYSTRAL reads image paths of same-user processes. This is read-only, but anti-cheat systems could theoretically flag handle opens. VYSTRAL uses the least-privileged right (`PROCESS_QUERY_LIMITED_INFORMATION`) and closes handles immediately. Detection of games started *outside* VYSTRAL (opt-in) opens no handles at all.
- **A second process at sign-in** (opt-in). It runs with the user's rights and touches only VYSTRAL's data folder. If the binary in `%LOCALAPPDATA%\Vystral` were replaced by malware, the sign-in entry would start it — but anything able to write there can already add its own sign-in entry, so this adds no new capability.
- **URI scheme nuisance.** A web page or another program can open VYSTRAL, or bring it forward on one of its own pages, through `vystral:` links. That is the whole effect (no data leaves, nothing runs), and browsers ask before opening external apps.
- **Rollback package tampering.** A program running as the same user could replace the preserved package *and* its manifest together, so the recorded hash only protects against corruption and partial writes, not against same-user malware (which could equally modify the install folder). Packages are not code-signed yet; signing would close this.
- **Deal links** from IsThereAnyDeal can point at any HTTPS shop (usually through ITAD's own redirect), and their terms forbid changing them. VYSTRAL opens them only in the default browser on a click, never inside the app. A compromised provider could still send a misleading shop link.
- **Cloud AI providers see what you ask.** With a provider turned on, that company receives the facts a feature lists (game titles, play totals, your question) under its own terms. It's off by default, opt-in per provider, listed per feature in Settings and next to every answer, and paused in Offline mode. A provider could return misleading wording; numbers it didn't get from VYSTRAL are discarded, but the choice of words and picks among VYSTRAL's candidates is the model's.
- **Third-party lookups reveal interest.** Each data-source request tells that provider that this IP asked about a game (or, for Wikidata and Steam prices, a batch of games). All are optional, listed in PRIVACY.md, and stopped by Offline mode.
- **Launch options** typed by the user are passed to the game as-is (validated for length and control characters). A user can still pass harmful options to their own game.
